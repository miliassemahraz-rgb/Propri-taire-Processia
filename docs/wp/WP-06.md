# WP-06 : Droits, clients, missions, affectations, configuration IA par client

- Statut : terminé (2026-11-26), branche `wp/WP-06-droits-missions`.
- Spécification : `docs/specs/increment-1.md`, sections 3.2, 3.3, 3.5, 4.1 et 7 (WP-06). Décisions : [PO-22] (visibilité des missions, décidée), [PO-12] (modèle léger par défaut, budget 150 €/mois), [PO-26] (déverrouillage par l'administrateur) et [PO-27] (invitations par le responsable), décidées. Nouvelles questions ouvertes : [PO-30] à [PO-33]. ADR 0012.

## Ce qui a été fait

- **`packages/policy`** : `can(sujet, action, ressource?)`, `MATRIX` (15 actions x colonnes `admin`, `manager`, `consultant`, `validator`), `personaFor`, `canSeeMission`. Fonctions pures. La colonne `observer` est le responsable de mission global non membre d'une mission (PO-22, PO-30) : lecture et commentaire, comme l'administrateur.
- **`PolicyModule`** (`apps/api/src/policy`) : `@Can(action)`, `@CurrentMission()`, `MissionContext` (`run(fn)` ouvre `withMission`) et `PolicyGuard` globale (évaluée après `SessionGuard`). `:missionId` invisible ou inexistant = 404 (identique), droit refusé sur mission visible = 403. Voir l'ADR 0012.
- **`UsersModule`** : `GET /users`, `GET /users/:id`, `PATCH /users/:id` (nom, rôle global, statut ; désactivation = sessions supprimées ; un administrateur ne se désactive ni ne se rétrograde). `POST /users/:id/unlock` déverrouille immédiatement un compte bloqué (`users.manage`, audité `auth.account_unlocked`) [PO-26]. `POST /invitations` passe à `@Can('users.invite')` (nouvelle action) [PO-27] : l'administrateur invite tout rôle ; le responsable de mission invite des consultants et des validateurs, uniquement pour une mission dont il est responsable affecté et avec le rôle de mission correspondant (sinon 403) ; les autres rôles reçoivent 403.
- **`ClientsModule`** : `GET /clients` (`mission.create`, pour choisir le client d'une mission), `POST`, `GET :id`, `PATCH :id` (`clients.manage`).
- **Configuration IA** (`ai_provider_configs`, une ligne par client) : `GET|PUT /clients/:id/ai-config` et `GET /ai-providers/:provider/data-policy` (`ai_providers.manage`).
  - Clé API chiffrée en AES-256-GCM (clé dérivée de `MASTER_KEY`, nouvelle variable obligatoire), jamais renvoyée : seulement `{ configured, masked }` (quatre derniers caractères). Clé absente de la requête = conservée ; chaîne vide = supprimée. Aucune clé dans `audit_log`.
  - Politique de données (texte dans `@processia/i18n`) affichée par la route dédiée ; un fournisseur autre que `fake` n'est enregistré qu'avec `acceptDataPolicy: true` (sinon 422 `POLICY_NOT_ACCEPTED`) ; `policy_accepted_by/at` et le texte accepté sont enregistrés ; une mise à jour sans nouvelle acceptation conserve l'acceptation tant que le fournisseur et le texte sont inchangés.
  - Contrôle des capacités : la réponse porte `warnings` (`CAPABILITY_MISSING` pour `text`, `documents`) ; la création de mission renvoie les mêmes avertissements pour le fournisseur du client (la mission est créée).
  - `models` : modèle par pipeline, clé réservée `default` ; aucun identifiant de modèle dans le code ni dans les valeurs par défaut (PO-12 : le choix du modèle léger par défaut revient à WP-09 / à la configuration). Budget mensuel par défaut : 150 €.
- **`MissionsModule`** : `GET /missions` (liste de suivi : phase, complétude du modèle de tête via `@processia/model`, soumissions en attente ; `progress` nul pour le validateur), `POST /missions` (rétention calculée depuis le client ; un responsable créateur devient responsable affecté), `GET|PATCH /missions/:missionId`, `GET|PUT /missions/:missionId/members`, `DELETE /missions/:missionId/members/:userId`. Un seul validateur par mission (409 ; index unique en base).
- Contrats (`packages/contracts/src/admin`), codes d'erreur `NOT_FOUND`, `CONFLICT`, `POLICY_NOT_ACCEPTED`, `MASTER_KEY` dans le schéma d'environnement, `.env.example`, CI, docker compose et RUNBOOK.
- Spécification 3.3, 3.5 et 8.1 (PO-22) mises à jour ; `docs/po/DECISIONS.md` : PO-30 à PO-33.

## Écarts et choix

1. **Visibilité (PO-22)** : la spécification 3.5 disait « les siennes » pour le responsable ; amendée (toutes). Pour les missions où il n'est pas membre, droits de lecture et commentaire seulement [PO-30].
2. **`MissionGuard` et `@Can`** réunis en une `PolicyGuard` (ADR 0012).
3. **Modification de nom, description et phase** : gardée par `mission.assign`, la matrice n'ayant pas d'action dédiée [PO-31].
4. Rôles affectables selon le rôle global, administrateur non affecté [PO-32]. `MASTER_KEY` et acceptation de la politique [PO-33].
5. Capacités par défaut déclarées `text` et `documents` pour `fake` et `anthropic` (modifiables par l'administrateur) ; la table n'a pas de champ `images` (la spécification 4.1 en a un) : à revoir avec WP-09.
6. La complétude de la liste de suivi parse l'instantané de tête à chaque appel (une transaction par mission) : correct pour quelques dizaines de missions ; une colonne dénormalisée sera utile avec WP-08.

## Dettes

- Pas de pagination des listes (missions, utilisateurs).
- Le texte de la politique de données d'Anthropic est un texte de travail à faire valider par le PO (CDC 6.7).
- Pas de réinitialisation du second facteur ni d'archivage de mission côté API.

## Suite : ce que WP-07, WP-08 et WP-09 doivent savoir

- **Toute route de mission** : `/missions/:missionId/...` avec `@Can(action)` et `@CurrentMission() ctx` ; `ctx.run(tx => ...)` ouvre la transaction RLS (`withMission`). Ne pas ouvrir `withMission` à la main. Mission invisible = 404 automatique. Un validateur membre est évalué avec `own: true`.
- **WP-08** : l'écriture du modèle porte `@Can('model.edit')`, le retour arrière `@Can('history.rollback')`. `missions.head_version` et `model_versions.snapshot` alimentent déjà la complétude de la liste de suivi (`MissionsService.progress`) ; garder `head_version` à jour. Remplacer la route de test `test-edit` du test d'intégration par les vraies routes.
- **WP-09** : `AiConfigService.find(clientId)` (exporté par `ClientsModule`) renvoie la ligne ; la clé se déchiffre avec `decryptSecret(row.apiKeyEnc, env.MASTER_KEY, KEY_PURPOSE)` (`apps/api/src/clients/ai-config.service.ts`, `auth/crypto.ts`). `models` est un dictionnaire pipeline vers identifiant ; la clé `default` s'applique aux pipelines non listés. Le modèle léger par défaut et le modèle principal « sur demande » (PO-12) sont à définir par la configuration, sans identifiant en dur. `monthly_budget_eur` vaut 150 par défaut. Ne rien appeler si la politique n'est pas acceptée (`policy_accepted_at` nul pour un fournisseur autre que `fake`).
- **WP-07** : textes d'erreur à traduire à partir des codes (`NOT_FOUND`, `CONFLICT`, `POLICY_NOT_ACCEPTED`, `CAPABILITY_MISSING`) ; `GET /clients` sert au choix du client à la création de mission ; `MissionSummary.myRole` nul = vue en lecture seule (administrateur ou responsable non membre) ; `progress` nul pour le validateur.
- Les tests d'intégration créent des sessions en enrôlant le TOTP de chaque compte du seed (voir `Client.signIn` dans `missions.int.test.ts`).

## Amendements PO-30 / PO-31

- **PO-30 (droits complets)** : la colonne `observer` est supprimée de `packages/policy` ; un responsable de mission global a la colonne `manager` sur toutes les missions, membre ou non. L'administrateur est inchangé (403 sur `model.edit`). Test table de `can()` réécrit (4 colonnes x 16 actions, plus un test dédié au responsable non membre). Tests d'intégration : un responsable non membre d'une mission créée par l'administrateur modifie le modèle, affecte et retire des membres et change la phase.
- **PO-31** : nom, description et phase restent gardés par `mission.assign` (administrateur et responsables). Un retour à une phase déjà validée par le client est refusé en `409 PHASE_REGRESSION` (nouveau code d'erreur, `details` : `kind`, `minimumPhase`).
- **Détermination de « validée par le client »** : lecture de `validation_submissions` (statut `validated`, RLS via `withMission`), sans nouvelle colonne. `analysis_dossier` validé : phase minimale `mapping` ; `as_is` validé : `transformation` ; `to_be` validé : `generation`. Les avancées et les retours vers une phase non verrouillée restent libres. Tant que WP-16 n'écrit pas de soumission `validated`, aucune mission n'est verrouillée en pratique ; la règle est testée en insérant ces lignes.
