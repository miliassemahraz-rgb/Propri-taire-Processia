# WP-05 : Authentification et double authentification

- Statut : terminé (2026-11-26), branche `wp/WP-05-auth`.
- Spécification : `docs/specs/increment-1.md`, sections 3.4 et 7 (WP-05). Décisions : [PO-3] (SSO reporté : mot de passe et TOTP) et [PO-4] (TOTP et codes de secours), validées ; [PO-25] et [PO-26] ouvertes.

## Ce qui a été fait

- **Contrats** (`packages/contracts/src/auth`) : schémas zod des requêtes et réponses, codes d'erreur stables (`MFA_REQUIRED`, `CSRF_INVALID`, `ACCOUNT_LOCKED`, `INVALID_CODE`, `INVITATION_INVALID`...), noms du cookie (`__Host-sid`) et de l'en-tête CSRF (`x-csrf-token`).
- **`AuthModule`** (`apps/api/src/auth`) :
  - `POST /auth/login` (mot de passe argon2id), `POST /auth/mfa/verify`, `POST /auth/mfa/enroll` (QR code PNG, URI `otpauth://` et clé de saisie manuelle), `POST /auth/mfa/confirm` (renvoie 10 codes de secours, une seule fois), `POST /auth/recovery`, `POST /auth/logout`, `GET /me`, `POST /invitations` (administrateur), `POST /invitations/:token/accept`.
  - **Sessions en base** (`sessions`) : seul le hachage SHA-256 de l'identifiant est stocké ; inactivité 30 min, durée maximale 12 h ; rotation de l'identifiant à la connexion et à la validation du second facteur (l'ancienne session est supprimée).
  - **Garde globale** `SessionGuard` (`APP_GUARD`) : sans `@Public()`, session valide exigée (`UNAUTHENTICATED`), jeton CSRF sur toute méthode non sûre (403 `CSRF_INVALID`), puis `mfa_verified_at` non nul (401 `MFA_REQUIRED`) sauf `@SessionOnly()` (étapes de connexion, `/me`).
  - **CSRF** : jeton synchronisé = HMAC(`SESSION_SECRET`, hachage de la session), renvoyé par les réponses de connexion et par `/me`, rejoué dans `x-csrf-token`. `login` et l'acceptation d'invitation (sans session) en sont exemptés ; `SameSite=Strict` les protège.
  - **TOTP** (`otplib`) : tolérance de ±1 pas (30 s), **anti-rejeu** par `users.totp_last_step` (mise à jour atomique conditionnelle) ; secret chiffré au repos en AES-256-GCM (clé dérivée de `SESSION_SECRET`).
  - **Codes de secours** : 10 codes `XXXXX-XXXXX`, stockés en HMAC ; consommés par un `UPDATE ... WHERE used_at IS NULL` atomique (usage unique) ; régénérés à l'enrôlement.
  - **Verrouillage** : compteur d'échecs consécutifs sur `users` (mot de passe, TOTP et code de secours confondus) ; le 6e échec verrouille le compte 15 min et ferme ses sessions ; le compteur ne repart à zéro qu'après un second facteur réussi. Adresse inconnue : même réponse et même temps (haché fictif).
  - **Limitation de débit** par IP (30 requêtes/min sur les routes d'authentification, en mémoire).
  - **Invitations** : jeton aléatoire 256 bits (haché en base), 72 h, usage unique par `UPDATE ... RETURNING` atomique dans la transaction qui crée le compte ; courriel envoyé par nodemailer (Mailpit en local) avec le texte dans `@processia/i18n` ; un mot de passe refusé ne consomme pas l'invitation. Mot de passe : 12 caractères minimum et liste locale de mots de passe courants.
  - **Journal** : `auth.login_succeeded`, `auth.login_failed`, `auth.mfa_enrolled`, `auth.mfa_verified`, `auth.mfa_failed`, `auth.recovery_used`, `auth.account_locked`, `auth.logout`, `auth.invitation_created`, `auth.invitation_accepted` dans `audit_log` (INSERT seulement).
- **Base** : migration `0003_auth_columns` (`users.failed_login_count`, `users.locked_until`, `users.totp_last_step`).
- **`apps/api` passe à `DATABASE_APP_URL`** (`DbModule`, sonde de santé comprise) : l'API ne tourne plus avec le compte d'administration.
- **Seed de développement** : les cinq comptes reçoivent le mot de passe `Processia-dev-2026!` (`DEV_PASSWORD`, argon2id précalculé dans `packages/db`) ; le TOTP s'enrôle à la première connexion. Outil `pnpm --filter @processia/api dev:totp <email>` pour obtenir le code courant. Documenté dans `docs/dev/RUNBOOK.md`.
- Documentation : `CLAUDE.md` et RUNBOOK ne décrivent plus `db:migrate` comme un squelette.

## Écarts et choix

1. **Limitation de débit** : la spécification dit « 5 tentatives par minute par compte et par IP, blocage progressif ». Le critère 4 exige que **six** échecs bloquent. Lecture retenue : 5 échecs tolérés, le 6e verrouille 15 min (par compte) ; `@nestjs/throttler` n'est pas utilisé (un plafond de 5 par minute rendrait le 6e échec indiscernable) ; un limiteur par IP maison (30/min) le complète. Pas de blocage progressif (durée fixe). [PO-25]
2. **`POST /invitations`** (création) n'était pas listé dans les interfaces mais l'invitation par courriel est dans le périmètre ; réservé à l'administrateur par un test de rôle direct, à remplacer par `@Can('users.manage')` dans WP-06. [PO-26]
3. **Login sans CSRF** : sans session, il n'y a pas de jeton à synchroniser ; protégé par `SameSite=Strict`.
4. **Comptes uniquement par invitation** : les comptes du seed existent déjà et se connectent avec le mot de passe de développement ; il n'y a pas de « mot de passe oublié » ni de changement de mot de passe (hors périmètre).
5. **`/me` accessible sans 2FA** (`@SessionOnly`) : il indique l'étape à franchir.
6. Liste de mots de passe compromis volontairement courte (une cinquantaine de valeurs) et locale.
7. L'enrôlement TOTP par un compte déjà enrôlé est refusé (409) ; il n'y a pas de réinitialisation du second facteur (WP ultérieur ou action d'administration).

## Dettes

- Le limiteur par IP est en mémoire : en multi-instances (WP-25), il faut un stockage partagé. `req.ip` est l'adresse du proxy tant que `trust proxy` n'est pas réglé (le web relaie `/api/*`) : à configurer avec le déploiement.
- Pas de tâche de purge des sessions expirées et des invitations échues (une session expirée est supprimée à sa première lecture).
- Les 6 échecs sont comptés par compte ; un attaquant peut donc verrouiller un compte connu (déni de service). Atténuation possible : déblocage par l'administrateur (PO-25).
- Le cookie `Secure` n'est utilisable que sur `localhost` ou en HTTPS.
- Pas de test E2E navigateur ni de page de connexion (WP-07). Aucun nouveau texte d'interface hors le courriel d'invitation (`email.invitation.*` dans `fr.json`).

## Suite : ce que WP-06 doit savoir

- La garde `SessionGuard` est globale : toute nouvelle route exige une session avec 2FA par défaut. Récupérer l'utilisateur avec `@CurrentAuth()` (`AuthContext` : `userId`, `user.globalRole`, `sessionId`). `@Public()` et `@SessionOnly()` sont dans `apps/api/src/auth/http.ts`.
- Les routes non GET exigent `x-csrf-token` (valeur `csrfToken` de la connexion ou de `/me`).
- Brancher `@Can(action)` après `SessionGuard` ; remplacer le test `globalRole !== 'admin'` de `InvitationsController.create`.
- `AuthModule` exporte `SessionsService`, `AuditService` et `CLOCK` (horloge injectable à réutiliser pour les tests). Pour une nouvelle écriture d'audit : `AuditService.record({ actorId, action, target, payload, ip })`.
- `DbModule` (global) fournit `DB` (connexion `processia_app`) ; `ENV` aussi. Pour les tests d'intégration d'API, reprendre le montage de `auth.int.test.ts` (`Test.createTestingModule`, surcharge de `ENV` et `CLOCK`, `app.listen(0)`).
- `MissionGuard` (spécification 3.3) peut s'appuyer sur `auth.user.globalRole` ; `missions` et `mission_members` ne sont pas cloisonnées par la RLS.
- Le jeton de coédition (`POST /missions/:id/collab-token`, WP-10) réutilise `COLLAB_JWT_SECRET` ; rien n'a été fait ici.
- Tests d'intégration : les fichiers partagent la base `processia_test` ; `vitest.int.config.ts` désactive désormais `fileParallelism` (un fichier à la fois) pour éviter les collisions entre remises à zéro.
