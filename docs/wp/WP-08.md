# WP-08 : Persistance versionnée du modèle, historique, retour arrière

- Statut : terminé (2026-11-26), branche `worktree-agent-a5d108d64f58b62d1`.
- Spécification : `docs/specs/increment-1.md`, sections 2.5, 3.2, 5.3, 5.4 et 7 (WP-08). Décisions : ADR 0013 ; nouvelles questions ouvertes [PO-50] à [PO-53].

## Ce qui a été fait

`apps/api/src/model/` (`ModelModule`, importé par `AppModule`) :

- **`ModelService`** (exporté) : `commit(missionId, cs, author, options?)` (ouvre `withMission`, pour les tâches de fond) et `commitInTx(tx, …)` (transaction de l'appelant). Il verrouille la ligne `missions` (`FOR UPDATE`), compare `baseVersion` à `head_version`, charge les diffs intercalés et appelle `rebase()` si la tête a avancé, applique `applyChangeSet(model, cs, { newId, at, userId, actor, submissionId })` avec un UUID v7 serveur (`uuidv7`, horloge `CLOCK`), puis écrit dans la même transaction `model_versions` (instantané, ChangeSet appliqué, diff), `model_version_elements`, `missions.head_version`, `post_validation_notices`, `notifications` et `pg_notify('mission_events', {missionId, version})`. Lecture : `getModel`, `listVersions`, `diff`, `elementHistory`. `rollback(tx, missionId, toVersion, author)` crée la version N+1 (fonction pure `buildRollback`).
- **`ProposalsService`** (exporté) : `create` (aperçu calculé, ChangeSet invalide non enregistré), `list`, `preview` (recalculé sur la tête : « adapté à la version N », ou passage en `stale`), `apply` (rebase puis commit dans un savepoint ; échec = `stale` enregistré puis `409`), `discard`. Après chaque commit, les propositions `pending` qui ne se rebasent plus passent en `stale`.
- **Routes** (`ModelController`, toutes sous `/missions/:missionId`) : `GET model?version=`, `GET model/versions`, `GET model/diff?from&to`, `GET elements/:eid/history` (`mission.read_workspace`) ; `POST model/changes` (`model.edit`, remplace la route de test) ; `POST model/rollback {toVersion}` (`history.rollback`) ; `GET proposals`, `GET proposals/:pid` (aperçu), `POST proposals/:pid/apply` et `…/discard` (`model.edit`).
- **Contrats** (`packages/contracts/src/model`) : requêtes zod et types de réponse ; codes d'erreur `STALE` (409) et `CHANGESET_INVALID` (422) ajoutés à `AUTH_ERROR_CODES`.
- Aide de test `apps/api/src/testing/http-client.ts` (client HTTP avec TOTP), exclue du build.
- `missions.int.test.ts` : la route `test-edit` est remplacée par `POST /missions/:id/model/changes` ; l'attente de complétude de la liste de suivi tient compte des versions créées par ces éditions.
- ADR 0013 ; [PO-50] à [PO-53] dans `docs/po/DECISIONS.md`.

## Écarts et choix

1. **Création de ChangeSet par route** : `POST model/changes` (nom libre, la spécification ne fixe pas la route d'écriture) ; la création de proposition n'a pas de route (elle viendra de WP-20) : `ProposalsService.create`.
2. **Le retour arrière n'a pas d'opération dans le méta-modèle** : le ChangeSet enregistré a `ops: []` et `rollbackTo`, le diff porte le changement (ADR 0013). Règles de validation : [PO-50].
3. **Le validateur ne lit pas le modèle de tête** (`mission.read_workspace`, matrice 3.5) : [PO-52].
4. **Signalement** : une notification in-app par version ; courriel reporté à WP-16 [PO-51].
5. **Éléments retirés** : un élément `validated` supprimé donne aussi un signalement.
6. **`aiCallId`** : conservé à l'application d'une proposition (celui de la proposition) ; `ai_calls` n'a pas de clé étrangère testée ici.

## Dettes

- Pas de pagination de la liste des versions ni de l'historique.
- Le chargement de la tête parse l'instantané complet (zod) à chaque commit ; correct à cette échelle (risque R-6), à revoir si les instantanés pèsent plusieurs Mo.
- `GET proposals/:pid` peut écrire (passage en `stale`).
- Pas d'instantané périodique avec diffs (R-6) ; pas de purge de versions.

## Suite : ce que les prochains WP doivent savoir

- **WP-10 (coédition)** : écouter `LISTEN mission_events` (charge `{missionId, version}`), charger l'instantané via `model_versions` et appliquer au `Y.Map` le diff minimal (`model_versions.diff`). Le `pg_notify` part à la validation de la transaction.
- **WP-11 / WP-12 (sources, extraction)** : appeler `ModelService.commit(missionId, cs, { userId, actor: 'ai' | 'system', aiCallId })` avec des ids `tmp:n`, ou `commitInTx` dans leur transaction `withMission`. Sur `STALE` (`AuthError` code `STALE`, `details.conflicts`), réconcilier de nouveau contre la tête et recommencer.
- **WP-16 (validation)** : les validations passent par `commit(…, { actor: 'validator' }, { submissionId })` ; les `post_validation_notices` et la notification `post_validation_notice` (payload : `version`, `noticeIds`, `elementIds`, `summaries`) existent déjà. À faire : lecture des signalements (`seen_at`), courriel [PO-19], lecture des versions figées par le validateur (`submission.read`) [PO-52].
- **WP-20 (dialogue)** : `ProposalsService.create(tx, missionId, { baseVersion, instruction, changeSet, explanation, createdBy, aiCallId })` ; `preview`, `apply`, `discard` sont déjà exposés en REST.
- **WP-07 / WP-13** : codes d'erreur à traduire : `STALE` (avec `details.conflicts`), `CHANGESET_INVALID` (`details` = erreurs d'intégrité de `@processia/model`). Réponses : `CommitResult` (`rebasedFrom` = « adapté à la version N », `warnings` de cohérence, `noticedElementIds`).
- Les tests d'intégration partagent la base `processia_test` : un fichier à la fois (déjà configuré).
