# WP-04 : Base de données, migrations et cloisonnement par RLS

- Statut : terminé (2026-11-26), branche `wp/WP-04-db-rls`.
- Spécification : `docs/specs/increment-1.md`, sections 3 et 7 (WP-04). Décisions : ADR 0003 et 0011, [PO-22].

## Ce qui a été fait

- **Schéma Drizzle** (`packages/db/src/schema/`) : les 26 tables de la spécification 3.2 (hors schéma `pgboss`, géré par pg-boss), clés `uuid` v7 (fonction SQL `uuid_v7()`), `citext`, `tsvector` français généré pour `source_chunks` (index GIN). `optimisation_decisions` porte une colonne `mission_id` en plus de la spécification 2.7, nécessaire à la RLS. Les contraintes `CHECK` imposent les énumérations.
- **Migrations** (`packages/db/migrations/`) : 0000 extensions et fonction, 0001 tables (drizzle-kit), 0002 contraintes, RLS et droits (SQL écrit à la main).
- **Rôles** : `processia_owner` (migrations, propriétaire des tables) et `processia_app` (non propriétaire, sans SUPERUSER ni BYPASSRLS), créés par l'amorçage de `pnpm db:migrate`. `audit_log` en ajout seulement pour `processia_app`.
- **RLS** : 15 tables cloisonnées, `FORCE ROW LEVEL SECURITY`, politique `mission_id = app_mission_id()` en lecture et en écriture (`USING` + `WITH CHECK`). Sans contexte : aucune ligne.
- **API** : `createDb`, `withMission(db, missionId, fn)` (transaction + `set_config('app.mission_id', …, true)`, uuid validé, transaction typée `MissionTx`), `withoutMission(db, fn, { aiUnscoped })`, `migrateDatabase`, `seedDevelopment`, `resolveDbUrls`.
- **Seed** (`pnpm db:seed`, idempotent) : un administrateur, un responsable de mission, deux consultants, un validateur, un client, la mission « Cabinet pilote » et ses affectations.
- **Aides de test** : `resetTestDatabase` (rôles, migrations, vidage), `withRollback`, `withMissionRollback`.
- **Commandes** : `pnpm db:migrate` (compile le paquet, amorce les rôles, migre), `pnpm db:seed`, `pnpm db:reset` (détruit les volumes, relance les services, migre et sème), `pnpm --filter @processia/db db:generate` (nouvelle migration).
- **Environnement** : `DATABASE_OWNER_URL` et `DATABASE_APP_URL` (facultatifs hors production) ajoutés au schéma zod et à `.env.example`.

## Écarts et choix

1. **`DATABASE_URL` reste le compte d'administration** : l'amorçage et le seed l'utilisent. `apps/api` (health) continue de l'utiliser ; il devra passer à `DATABASE_APP_URL` (WP-05).
2. **`ai_calls.mission_id` facultatif** : les lignes sans mission ne sont accessibles qu'avec `app.ai_unscoped = 'on'` (voir ADR 0011), pour respecter « sans contexte, 0 ligne ».
3. **Colonnes JSONB typées `unknown`** (`snapshot`, `change_set`, `diff`, `warnings`, `locator`, `payload`) avec `TODO(WP-02)` : à typer avec `@processia/model`.
4. **Seed sans mot de passe** : `password_hash` reste nul (l'argon2id et le TOTP arrivent avec WP-05). Les comptes existent mais ne peuvent pas encore se connecter.
5. **`db:reset` sème en plus** de migrer (commodité de développement) ; `db:seed` refuse de tourner en production.
6. **Peu d'index** : seuls ceux de l'usage évident (clés étrangères de recherche, historique, plein texte). À compléter selon les requêtes réelles (WP-08, WP-11).
7. **Pas de test Nest** : les tests de ce WP appellent directement la bibliothèque.

## Dettes

- Les clés étrangères ne garantissent pas la concordance de `mission_id` entre parent et enfant (hors `model_version_elements`) ; les dépôts doivent écrire dans le contexte de la mission courante (ADR 0011).
- Les instructions de `CLAUDE.md` et du RUNBOOK mentionnent encore `db:migrate` comme squelette : à mettre à jour par l'orchestrateur (hors périmètre de ce WP).

## Suite : ce que les prochains WP doivent savoir

- **WP-05** : `users.password_hash` est nul dans le seed ; table `sessions` avec `id_hash` unique ; `recovery_codes` et `auth_identities` prêts. Le journal d'authentification va dans `audit_log` (INSERT seulement).
- **WP-06** : `MissionGuard` décide de l'accès **avant** `withMission()` : administrateur et responsables de mission voient toutes les missions, consultant ses affectations, validateur la sienne [PO-22]. La RLS ne distingue pas les rôles. `missions` et `mission_members` ne sont pas cloisonnées : filtrer dans l'application. Utiliser `withoutMission(db, …)` pour ces tables, `withMission` pour les autres ; une table cloisonnée lue hors contexte paraît vide.
- **WP-08** : `model_versions` a pour clé (`mission_id`, `version`) ; `missions.head_version` vaut 0 sans version. Écrire dans `model_versions` et `model_version_elements` dans la même transaction `withMission`.
- **Nouvelle table cloisonnée** : colonne `mission_id`, migration avec politique, ajout à `MISSION_SCOPED_TABLES` (le test d'intégration échoue sinon).
- Les tests d'intégration partagent la base `processia_test` : `resetTestDatabase(resolveDbUrls(process.env, { test: true }))` en `beforeAll`. Plusieurs fichiers de test en parallèle vident les mêmes tables ; en ajouter d'autres suppose un fichier à la fois (`fileParallelism`) ou des schémas distincts.
