- Statut : terminé (2026-11-26), branche `worktree-agent-a176933037e719eda`.
- Spécification : `docs/specs/increment-1.md`, sections 6.1, 6.2 et 7 (WP-18). Décisions : [PO-1] (validée), [PO-2] et [PO-20] (valeurs par défaut appliquées) ; questions nouvelles : [PO-40] à [PO-43]. ADR 0012.
- Jeux de test : `buildMinimalModel`, `buildCompleteModel` (WP-02, WP-03) et un modèle « riche » écrit pour ce WP (`packages/bpmn/src/test-support.ts`). WP-17 n'est pas terminé : les enchaînements réalistes de la chaîne pilote restent à rejouer (voir « Suite »).

## Ce qui a été fait

Dans `packages/bpmn` (paquet pur ; dépend de `@processia/model`, `bpmn-moddle`, `elkjs`, `fflate`) :

- **`listDiagrams(model)`** : `L0`, `L1:<macro>` pour chaque macroprocessus, `L2:<processus>` pour chaque processus (sous-processus compris), `L3:<tâche>` pour chaque tâche qui a des étapes (PO-2).
- **`toBpmn(model, diagram, options?)`** : `Promise<{ xml, layoutOps }>`. `toBpmnCombined(model)` : un seul `definitions` avec tous les diagrammes. `exportBpmnZip(model)` : un `.bpmn` par diagramme (`L0.bpmn`, `L1-<uuid>.bpmn`…) et `cartographie-complete.bpmn`, ZIP reproductible (dates fixes, entrées triées).
- **Niveau 0** : un processus « Cartographie globale », une `callActivity` par macroprocessus, un `group` par catégorie (pilotage, réalisation, support), une `sequenceFlow` par lien `sequence`, une `textAnnotation` et une `association` pour les autres liens.
- **Niveau 1** : collaboration à un participant (le macroprocessus), un couloir par acteur, une `callActivity` par processus (`calledElement` = processus du niveau 2), enchaînement par `order`.
- **Niveau 2** : collaboration, participant « Organisation » avec un couloir par acteur interne, un participant fermé par acteur externe ou système tiers, tâches typées (`userTask`, `manualTask`, `serviceTask`, `sendTask`, agent IA = `serviceTask` avec `processia:AiAgent`), `callActivity` pour les sous-processus, événements de début, de fin, intermédiaires et de bord (minuteur, message, erreur, signal, conditionnel), passerelles exclusive, parallèle et inclusive, flux de séquence avec condition et flux par défaut, `messageFlow`, `dataObjectReference` avec `ioSpecification` et associations d'entrée et de sortie, `documentation` (règles applicables, description).
- **Niveau 3** : processus dédié avec un `subProcess` développé (étapes, événements de bord pour les exceptions, passerelles), objets de données dont les champs sont dans la `documentation`, règles en `textAnnotation`.
- **Identifiants** : `Activity_<uuid sans tirets>`, `Event_`, `Gateway_`, `Flow_`, `MessageFlow_`, `Process_` ; les formes répétées d'un diagramme à l'autre (couloirs, bassins, objets de données) sont suffixées par la clé du diagramme, donc uniques dans le fichier combiné. `elementIdFromBpmnId` fait l'inverse. Chaque forme et chaque lien correspondant à un élément du modèle porte `processia:elementId` (espace de noms `urn:processia:bpmn:1`, descripteur moddle `PROCESSIA_DESCRIPTOR`). Les flux déduits de l'ordre (niveaux 1 et 3) portent `processia:derived="true"`.
- **Mise en page** (ADR 0012) : elkjs donne les colonnes, le code place les couloirs, empile, trace les liens, produit le BPMN DI et réutilise les positions mémorisées. `layoutOps` ne contient que les positions nouvelles ou changées (`set_layout`, à appliquer avec la cause `layout`).
- CI : `xmllint` installé avant les tests ; navigateur Playwright installé avant les tests d'intégration (le test bpmn-js est un `*.int.test.ts`).

## Écarts par rapport à la spécification

1. **`toBpmn` est asynchrone** (`Promise<{ xml, layoutOps }>`) : elkjs et `bpmn-moddle.toXML` le sont. `listDiagrams` est synchrone.
2. **Le niveau 3 est un processus dédié** contenant un `subProcess` développé (la spécification laisse le choix). Au niveau 2, la tâche reste une tâche.
3. **Mise en page** : elkjs ne fait que les colonnes ; couloirs et routage sont faits par le code (ADR 0012, repli documenté). Les liens peuvent croiser des formes.
4. **Flux d'information** : seuls ceux qui franchissent un bassin sont dessinés en `messageFlow` (PO-40). Un flux sans `activityId` n'apparaît dans aucun diagramme.
5. **Pas de `CartographyModule` ni d'API** (`GET /missions/:id/bpmn/...`) : `apps/` est hors du périmètre de cet agent ; le paquet expose ce qu'il faut (voir « Suite »).
6. **Pas de structure de vue simplifiée** : la spécification l'attribue à WP-19, pas à WP-18.
7. Le niveau 1 enchaîne les processus par `order` (flux déduits, `processia:derived`). Un processus ou une tâche sans acteur va dans un couloir « Non affecté ».
8. `test-support.ts` est exclu du build. Dépendances ajoutées : `bpmn-moddle`, `elkjs`, `fflate` ; en développement `bpmn-js`, `@playwright/test`.

## Dettes

- Routage simple : les flux de message traversent les couloirs, les libellés de deux événements de bord voisins se chevauchent, les liens des objets de données peuvent croiser d'autres liens.
- `xmllint` doit être présent pour le test XSD (installé en CI) ; sans lui le test est ignoré.
- Le test bpmn-js exige Chromium ; sur la machine des agents : `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/opt/pw-browsers/chromium pnpm test:int`.
- Les positions mémorisées d'éléments supprimés restent dans `layout` (sans effet).

- **WP-19** : une `callActivity` a pour `calledElement` l'identifiant du processus BPMN du niveau inférieur (`Process_<uuid de l'activité>`) ; le diagramme correspondant est `L1:<macro>` ou `L2:<processus>`. Dans le fichier combiné, l'identifiant du diagramme est `Diagram_<uuid sans tirets>` (`Diagram_L0` pour le niveau 0). La vue simplifiée et l'alternative textuelle se construisent à partir du modèle, pas du BPMN.
- **WP-24** : interopérabilité Camunda Modeler et demo.bpmn.io [PO-20] : seul bpmn-js est testé (ce qui couvre demo.bpmn.io) ; le XSD valide et l'extension `processia` est ignorée par les autres outils. Un test manuel de Camunda Modeler reste à faire.
