## Ce qui a été fait

`packages/ai` (SDK officiel `@anthropic-ai/sdk`, `zod`) :

- `types.ts` : `AiProvider`, `StructuredRequest/Result` de la spécification 4.1, plus `model` (résolu par l'exécuteur), `context` (second bloc système mis en cache) et `warnings`.
- `fake-provider.ts` : `FakeProvider` (enregistrement exact `<dir>/<pipeline>/<inputHash>.json`, scénario par pipeline, repli générique construit depuis le JSON Schema avec avertissement), simulations `refusal`, `max_tokens`, JSON invalide (`FakeSimulation`), validation de toute sortie par le schéma de la requête ; `RecordingProvider` (mode `AI_RECORD=1`).
- `anthropic-provider.ts` : `AnthropicProvider` (`output_config.format` via `zodOutputFormat`, `thinking` adaptatif, effort, `cache_control` sur le système et le contexte, PDF en bloc `document`, images en bloc `image`, ni prefill ni `tool_choice`), `max_tokens` doublé une fois, refus, erreurs typées (400/404/auth non réessayables, 429, 5xx, réseau).
- `runner.ts` : `runPipeline` / `runPipelineDetailed` (budget, résolution du modèle, appel, schéma, contrôle sémantique, une seule reprise de réparation, journal, coût estimé, alerte à 80 %). `pricing.ts` (table de prix configurable), `prompts.ts` (`prompts/<pipeline>.fr.md`, variables `{{…}}`), `hash.ts` (empreinte), `guard.ts` (garde-fou CI), pipeline `demo.summary`, `smoke.ts`.
- `apps/api/src/ai` : `AiModule` (importé par `AppModule`), `AiProviderRegistry.forClient` (lit `AiConfigService.find`, déchiffre la clé, refuse un fournisseur réel sans politique acceptée, factice sans clé, `AI_PROVIDER_OVERRIDE=fake`), `AiCallsService` (écriture `ai_calls` sous `withMission` ou `aiUnscoped`, dépense mensuelle), `AiService.run(def, input, { clientId | missionId, userId })` (point d'entrée des WP aval ; audit `ai_budget.alert_80`).
- Variables d'environnement : `AI_PROVIDER_OVERRIDE`, `AI_RECORD`, `AI_RECORDINGS_DIR`, `AI_PRICE_TABLE`, `AI_BASE_URL` (schéma zod, `.env.example`, RUNBOOK). Script racine `pnpm ai:smoke`.

## Écarts

- **Repli côté serveur** (bêta `server-side-fallback`, spec 4.3) non implémenté : le nom de la bêta n'est pas vérifiable sans clé. Le modèle réellement servi est tout de même journalisé (`model` de la réponse).
- Les pipelines métier (`extraction.chunk`, etc.) ne sont pas créés : ils relèvent de WP-12, WP-14, WP-17, WP-20, WP-21, WP-22.
- Pas de migration : `ai_calls` suffit (ADR 0013).
- `AI_PROVIDER` (valeur globale existante) n'est pas utilisé par le registre : la configuration vient de `ai_provider_configs`.
- Aucun enregistrement exact livré dans `packages/test-fixtures` (aucune clé) ; le dossier se règle par `AI_RECORDINGS_DIR`.

## Dettes

- Dépense mensuelle : une requête par mission du client à chaque appel (ADR 0013).
- Concurrence : deux appels simultanés peuvent dépasser le plafond d'un appel.
- `AI_PRICE_TABLE` à renseigner [PO-61] ; tarif par défaut approximatif.

## Suite (pour WP-11, WP-12, WP-14)

- Appeler `AiService.run(pipelineDef, input, { missionId, userId })` ; le résultat donne `output`, `callId` (à stocker dans `ai_call_id` des versions et propositions), `usage`, `costEstimateEur`. Importer `AiModule`.
- Écrire les `PipelineDef` (prompt via `loadPrompt('<pipeline>')` dans `packages/ai/prompts/<pipeline>.fr.md`) et leurs scénarios factices via `AiProviderRegistry.registerFakeScenario(pipeline, fn)` ; un scénario peut renvoyer `FakeSimulation.refusal()` etc. Le repli générique ne convient pas aux scénarios du pilote.
- WP-12 : le déclassement des citations non retrouvées (spec 4.5) se fait dans `semanticCheck` ou après `run` ; le compteur de qualité est à ajouter au `response` du journal si besoin.
- WP-11 (`extraction.document_visual`) : passer les pièces jointes dans `attachments` ; le journal n'en garde que les métadonnées.
- Capacités : `forClient` ne vérifie pas encore les capacités exigées par pipeline.
